Hosting & infrastructure Q1–6

Q-01

Actual production hosting architecture?

HostingVerified

Cloudflare's global edge network in front of a single DigitalOcean App Platform origin, DigitalOcean Managed PostgreSQL, and DigitalOcean Spaces for uploaded images. Two separate deployed apps: unify-platform (admin + dealer portal) and unify-dealer-site (the public dealer websites, one codebase serving every dealer by domain). No physical servers, no per-dealer infrastructure. One caveat worth knowing internally: the Cloudflare layer is DigitalOcean's own managed edge, not a separately-purchased Cloudflare account — same protection, just not a line item we control independently.

Q-02

Where is the application hosted?

HostingVerified

DigitalOcean App Platform, Sydney region.

Q-03

Where is the database hosted?

HostingVerified

DigitalOcean Managed PostgreSQL 16, Sydney. Currently a single node (no standby/failover replica — see Q29–31).

Q-04

What providers/services are involved?

HostingVerified
  • DigitalOcean — compute, database, object storage/CDN
  • Cloudflare — edge/TLS (via DO, see Q1)
  • Resend — transactional email (portal OTPs, invites, notifications)
  • Web3Forms — dealer website contact form (third party, see Q51)
  • Google — Maps/Places API, Analytics (GA4)
  • Groq — AI provider for the site chat assistant (currently disabled)
  • GoDaddy — domain/DNS registrar
  • GitHub — source control, CI
Q-05

What regions/countries is data stored or processed in?

HostingVerified

All storage and processing — app compute, database, file storage — is in Sydney, Australia. Cloudflare's edge terminates TLS at whichever point-of-presence is nearest the visitor (e.g. Auckland for NZ traffic), but that's connection handling, not data storage — no customer data is stored there. Practically: dealer and customer data lives outside New Zealand, in Australia. Worth flagging to whoever writes the privacy policy (Q67) since this has Privacy Act implications we're not qualified to rule on ourselves.

Q-06

Is all traffic HTTPS with auto-renewed SSL?

HostingVerified

Yes, for every domain currently live — confirmed on the platform domain and dealer domains (e.g. stihlshoptauranga.co.nz) with valid, auto-renewing certificates via DigitalOcean's managed TLS. One nuance: adding a new dealer's domain to the app today is a manual admin step, not an automated onboarding pipeline — but once added, cert issuance and renewal are fully automatic from then on.

Authentication & access control Q7–18

Q-07

How does dealer authentication work?

AuthVerified

Email + password, then a one-time email code as a second factor, then a signed JWT session token.

Q-08

What technology/provider handles 2FA?

AuthVerified

Self-built email OTP — a time-limited code generated server-side, delivered via Resend, verified server-side. Not a dedicated 2FA provider like Twilio/Authy.

Q-09

Are passwords ever stored directly by F925?

AuthVerified

Passwords are hashed with argon2 (a modern, industry-standard password hashing algorithm) before storage — never stored or logged in plaintext, and not reversible.

Q-10

Is access controlled server-side so one dealer can't see another's data?

AuthPartial

Every dealer route scopes its database queries by the dealer ID carried in the authenticated session token, and the pattern is consistent everywhere we've checked. We have not run a dedicated line-by-line authorization audit of every single endpoint to formally certify there's no gap — reasonably confident based on the pattern, not yet formally verified end-to-end.

Q-11

What user roles currently exist?

AuthPartial

Checked directly against the production database: two role types exist structurally — admin (F925 staff; one active account in production, hello@f925.works) and dealer (3 accounts in production — Tauranga, Waihi, Rotorua). Admin vs. dealer isn't a data field, it's structural — separate tables, separate login flow, separate session claim. Doesn't exist yet: a STIHL-level role (e.g. read-only network-wide view) — buildable on top of the existing role system, but not there today.

Q-12

Are authentication/login attempts logged?

AuthNot yet

No dedicated login-attempt audit log exists today. Buildable before rollout.

Q-13

Is there brute-force/rate-limit protection?

AuthNot yet

Not currently implemented on login endpoints. Already on our own list to build.

Q-14

How are password resets handled?

Token-based, time-limited reset link sent by email via Resend.

Q-15

We haven't independently verified whether an already-issued session token is invalidated instantly on disable, or simply expires naturally on its own timer — worth confirming before stating a guaranteed "instant" cutoff.

Q-16

AuthVerified

DigitalOcean App Platform environment variables, encrypted at rest by DO. Confirmed no secrets are committed to either repository — full source sweep done, nothing hardcoded found.

Backups & disaster recovery Q23–30

Q-23

What automated backups currently exist?

BackupsVerified

Checked directly against the live database: automated daily backups are running as a built-in part of DigitalOcean's managed Postgres service. This corrects an earlier internal assumption that backups weren't running at all — they are, and have been. What's still missing is a documented, tested restore process (Q28–30).

Q-24

How frequently is the database backed up?

BackupsVerified

Daily — confirmed one snapshot per day.

Q-25

How long are backups retained?

BackupsPartial

At least 8 days of daily backups currently visible on the account. That's an observation, not a confirmed contractual retention policy from DigitalOcean's documentation — worth stating as "at least a week" rather than a precise guaranteed number until confirmed against DO's plan-specific policy.

Q-26

Are dealer-uploaded images/assets backed up too?

BackupsVerified

Yes. Uploaded images live in DigitalOcean Spaces, itself redundant, durable object storage by design. On top of that, object versioning is now enabled on the images bucket (turned on and confirmed live this week) — any overwrite or delete at the storage level keeps the previous version recoverable, at no extra cost (included in the existing $5/mo Spaces plan; well under its 250 GiB storage allowance). Worth knowing separately: the app's own upload/delete code already avoids this risk by design — every upload gets a unique filename rather than overwriting one, and removing a photo in the portal only unlinks it from the dealer's profile rather than deleting the file, so nothing is actually destroyed by normal use in the first place. Versioning covers the remaining case: a direct deletion or overwrite at the storage level itself.

Q-27

Where are backups stored?

BackupsVerified

Within DigitalOcean's managed database service, same Sydney region.

Q-28

Have restores from backup actually been tested?

BackupsNot yet

No — the backups exist and run automatically, but no one has performed and logged an actual test restore. This is the honest gap: backups existing isn't the same as a proven, rehearsed recovery process.

Q-29

Realistic RPO — maximum recent data loss in a catastrophic event?

BackupsPartial

Based on daily backups alone, worst case is up to 24 hours of data loss (everything since the last nightly snapshot). This could be tightened significantly with point-in-time recovery, which DigitalOcean's managed Postgres supports but isn't currently confirmed as configured — worth checking before quoting a tighter number.

Q-30

Realistic RTO — how quickly could we restore service after a major failure?

BackupsNot yet

No tested/timed answer exists yet, because no restore has been rehearsed (Q28). Any number stated today would be a guess, not something we've proven. This should be one of the first things run before making an RTO commitment.

Uptime & monitoring Q31–37

Q-31

Can we confidently commit to STIHL's 99.9% uptime?

UptimePartial — priced, not yet built

Not on the current setup — both the app and the database run as a single instance with no standby/failover, and there's no uptime monitoring to measure against a target (Q33). But the path to a genuine commitment is concrete and priced, checked against DigitalOcean's actual current rates:

  • App redundancy — a second App Platform instance for the dealer-facing site: $12/mo → $24/mo total (+$12/mo). DO load-balances across both automatically; losing one is invisible to visitors.
  • Database redundancy — our current tier only supports 1 node at all (no standby option exists on it). A standby requires moving up one tier: DO's published minimum for that is $30/mo primary + $30/mo standby = $60/mo total, versus $15/mo today (+$45/mo).

Total: +$57/month to make 99.9% a real, backed claim rather than a target — plus choosing and wiring up an actual uptime-monitoring tool (Q33), which is a decision to make, not priced here. Recommendation: quote this as "committing to 99.9% as part of rollout, with the infrastructure spend built into the proposal" rather than promising it on what's running today.

Scale & shared-platform risk Q70–74

Q-70

Anything technically preventing scaling from 3 dealers to ~92?

ScaleVerified

No — the architecture is already built for this (one codebase serving every dealer by domain lookup, one database with per-dealer rows). Scaling to 92 is a matter of onboarding volume, not an architectural limit.

Q-71

Does that scale create meaningful hosting cost/limitation changes?

ScalePartial

Current compute/database tiers are sized for a handful of dealers, not 92 — instance size and database tier will need upgrading as real traffic grows, which has a real (but not yet quoted) cost impact. Nothing structural blocks it, just needs the resource tier bumped alongside rollout.

Q-72

Could an issue with one dealer affect the wider network?

ScaleVerified

Honest answer: yes, in principle — it's a shared codebase and shared compute/database, so a bug affecting the shared code path or an outage on the shared app instance affects everyone, not just one dealer. This is the direct tradeoff of "one deploy updates every dealer at once," which is also the platform's core strength (see Q73 for what limits the blast radius).

Q-73

What controls/isolation exist to minimise that risk?

ScalePartial

Data is isolated per dealer at the database level (Q10) — one dealer's data or content changes can't corrupt another's. What's not yet in place: the redundancy (Q31) that would stop a full outage from taking down every dealer at once, and a staging environment (Q21) to catch a bad shared-code change before it reaches production.

Q-74

What's the actual disaster-recovery process, start to finish?

ScaleNot yet

Honestly: there isn't a documented, rehearsed one today. What exists: automated daily database backups (Q23) and a redeployable app via DO's deployment history (Q22). What's missing: a written runbook, a tested restore (Q28), and a proven RTO/RPO (Q29–30). This is the single most important gap to close before making any DR claim to STIHL.
